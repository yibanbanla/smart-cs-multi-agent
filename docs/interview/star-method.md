# STAR 面试话术

> 面向当前 Python 版本整理，适合讲项目、讲难点、讲技术取舍。

---

## 场景一：请介绍一下你的项目

### S

公司客服系统面临咨询量大、知识分散、人工响应慢以及高风险内容缺乏自动审查等问题。

### T

我负责设计并实现一套基于多 Agent 架构的智能客服系统，希望把常见咨询自动化处理，同时补上知识检索、工单流转和合规审查能力。

### A

- 采用 Supervisor 编排模式，把意图路由、知识检索、工单处理、合规审查拆成独立 Agent
- 设计分层记忆系统，解决多轮对话上下文丢失问题
- 引入 RAG 机制，让回答建立在知识库内容之上
- 把外部工具统一封装为 MCP 风格接口，降低接入成本
- 接入 OpenTelemetry 做全链路追踪，便于排查慢请求和错误链路

### R

- 首问解决率提升
- 人工处理压力明显下降
- 平均响应时间降到秒级
- Token 成本与排障成本都得到控制

---

## 场景二：你遇到过什么技术难点

### S

项目初期，多 Agent 串联后最棘手的问题是流程控制和状态一致性。尤其是合规审查必须成为稳定兜底，而不是某些分支下的可选步骤。

### T

我需要保证不管用户问题走哪个业务 Agent，最终结果都能进入统一的审查流程。

### A

- 使用 LangGraph 的 StateGraph 显式定义节点和边
- 把合规审查设为汇聚节点
- 用统一 `AgentState` 保存所有子 Agent 输出
- 在 Supervisor 中做最终汇总和失败兜底

### R

流程稳定性明显提升，后续新增业务节点时也不需要重写整套主流程。

---

## 场景三：为什么选这个技术栈

### 回答思路

- 选 Python，是因为 AI 工具链成熟，LangGraph、向量检索和实验效率都更好
- 选 LangGraph，是因为它对状态编排、条件路由、检查点恢复支持比较完整
- 选 FastAPI，是因为异步能力和接口开发体验都很好
- 选 Redis + FAISS，是因为它们足够支撑本项目的本地验证和演示需求

## 通用模板

```text
S: 当时系统面临什么业务问题，问题有多严重
T: 你负责什么，目标是什么
A: 你做了哪些关键设计和取舍，为什么这么做
R: 最终结果如何，最好带数字
```

## 表达建议

1. 先讲业务问题，再讲技术设计
2. 不只说用了什么，要说为什么这样选
3. 每个关键动作尽量对应一个结果
4. 如果结果还没上线，也可以讲验证指标或预期收益
